# Full-Stack Integration Report

CBE Enterprise ATM & ICT Support Management System — Django REST backend + React/TypeScript frontend.

## 1. System overview

Internal enterprise system for managing CBE organizational hierarchy (districts → branches → ATMs), ATM incident lifecycle (report → acknowledge → assign → investigate → troubleshoot → escalate → resolve → verify → close), notifications, audit, and reporting. Django is the single authority for authentication, authorization, roles, organizational scope, business rules, and persistence; React provides presentation only.

## 2. Architecture

- **Backend:** Django 5 + DRF, SimpleJWT (access 30 min / refresh 1 day, blacklist enabled), django-filter, drf-spectacular (`/api/schema/`, `/api/docs/`), CORS for the Vite dev server. Apps: `accounts`, `organization`, `assets`, `incidents`, `notifications`, `audit`, `reports`, `common`.
- **Frontend:** React 18 + TypeScript + Vite, React Router 6, TanStack Query 5, Axios client with Bearer-token interceptor and 401 redirect, custom CSS design system.
- **Database:** PostgreSQL configured for production; SQLite fallback for local development (`USE_SQLITE=true`).

## 3–6. Roles, responsibilities, permissions, scope

Roles on `User.role`: `DISTRICT_ADMIN`, `OPERATIONS_OFFICER`, `MAINTENANCE_SUPERVISOR`, `TECHNICIAN`, `BRANCH_MANAGER`, `BRANCH_USER`, and `AUDITOR`. Legacy `ADMINISTRATOR`, `SUPERVISOR`, and `MONITORING_OFFICER` accounts are normalized at runtime so previously created users remain usable.

Enforcement layers:
1. **Authentication** — all endpoints require a valid JWT.
2. **Role permissions** — `apps/common/permissions.py`: district administrators manage users and organization records; maintenance supervisors assign, verify and close; technicians additionally troubleshoot, escalate and resolve; branch users are limited to their branch's ATM status and fault reports.
3. **Organizational scope** — `ScopedQuerysetMixin.scope_queryset` on every resource viewset: staff/head office see everything, district users see their district, branch users their branch. Out-of-scope updates return 403; deletes are always forbidden (deactivate instead).
4. **Frontend gating** — sidebar items, routes (`PermissionRoute`) and buttons are driven by the `permissions[]` list returned by `GET /api/auth/me/`. This is UX only; the backend independently enforces everything.

## 7. Database

User → role/scope (district FK, branch FK) → District → Branch → ATM → Incident → TroubleshootingAction / Escalation / Resolution (1:1) / Verification (1:1). AuditLog and Notification reference users and incidents.

## 8. APIs

- Auth: `POST /api/auth/token/` (username or email), `POST /api/auth/token/refresh/`, `POST /api/auth/logout/` (blacklists refresh), `GET /api/auth/me/` (includes computed `permissions[]`).
- Resources: `/api/districts/`, `/api/branches/`, `/api/atms/`, `/api/incidents/`, `/api/users/`, `/api/audit-logs/`, `/api/notifications/` (+ `unread_count/`, `{id}/mark_read/`, `mark_all_read/`). All support server-side search, filtering and ordering.
- Incident workflow actions: `assign/`, `status/` (validated state machine), `troubleshooting/` (GET/POST), `escalate/`, `resolve/`, `verify/` — all transactional and audited.
- Reports: `/api/reports/dashboard/`, `/reports/districts/`, `/reports/branches/`, `/reports/technicians/`, `/reports/atms/{id}/` — all scope-aware aggregates.

## 9–11. Authentication, frontend, backend integration

Central `AuthProvider` exposes currentUser (with permissions), isAuthenticated, isLoading, login/logout/refresh. Tokens live in localStorage; logout blacklists the refresh token server-side. The axios response interceptor clears the session on 401. Route protection via `ProtectedRoute` + `PermissionRoute`; access-denied and 404 pages included.

## 12–21. Functional coverage

- **Dashboards:** single scope-aware dashboard fed by `/api/reports/dashboard/` aggregates (ATM totals/status mix, open/critical/escalated incidents, availability %) plus recent incidents; header date and scope label are derived at runtime — no hardcoded statistics anywhere.
- **ATM management & monitoring:** list/search/filter by status; branch/district shown from server data.
- **Incidents:** creation with auto-derived district/branch, detail page with breadcrumb, workflow action buttons per state, troubleshooting history, escalation, resolution, verification.
- **Notifications:** generated by the backend on critical create, assignment, escalation, resolution and closure; notification center with unread badge, mark-read/mark-all-read.
- **Audit:** every incident transition plus district/branch/ATM/user create-update writes AuditLog rows; readable audit page with search.
- **Reports:** district performance (availability, incidents, escalations), branch overview with common categories, technician workload with average resolution hours, per-ATM report endpoint.

## 22. Testing

Backend pytest suite covers authentication, scope, workflow, branch reports, and portal-account provisioning.
- auth: invalid login rejected; `/me` returns permissions for supervisor vs technician.
- scope: district-A manager sees only district-A ATMs/incidents; cross-district access 404; branch manager cannot create districts (403); head office can.
- lifecycle: full REPORTED→…→CLOSED flow including failed verification path, permission denials (technician cannot acknowledge/verify), audit rows for every step, notifications at each stage.
- reports scoped correctly; notification endpoints function.

Frontend: `npm run build` passes with zero TypeScript errors; no mock/dummy/fake data in source.

## 23. Security

JWT-only API, blacklist on logout, role+scope enforced server-side on every mutation, deletes disabled in favor of deactivation, out-of-scope object access returns 403/404, frontend permission checks are cosmetic only.

## 24. Deployment

Set `DJANGO_DEBUG=false`, `DJANGO_SECRET_KEY`, `DJANGO_ALLOWED_HOSTS`, `DATABASE_URL` (PostgreSQL), `USE_SQLITE=false`, and `CORS_ALLOWED_ORIGINS`. The Render blueprint installs dependencies, runs migrations before deploy, and serves Django through Gunicorn. Frontend: set `VITE_API_BASE_URL` to the production API and run `npm run build`.

## 25. Known issues

- Global DRF pagination is not enabled; list endpoints currently return full arrays (filtering is server-side). Enable `PAGE_SIZE` before datasets grow large.
- Reports and dashboards are API-backed; export/download jobs still need to be added if operational teams require CSV or PDF files.
- No automated E2E browser tests yet; the end-to-end workflow is covered by the backend integration test and manual UI passes.
- User creation UI manages activation/roles but not password provisioning flows (invitations/reset).

## 26. Future improvements

WebSocket/push notifications, CSV/PDF report exports, global entity search endpoint, organization tree visualization, SLA timers and breach alerts, ATM telemetry ingestion, per-role dashboard variants, OpenAPI-generated typed client.
